# Hi3D + 半天：双人 3D 游戏原型

> 历史方案：2026-11-08 已确认转向派对竞速闯关，当前方向见[派对游戏调研](party-racing-research.zh-CN.md)。本页双人搬运与弹道对战是旧候选，不能直接作为新方向的实施计划或工期承诺。

更新：2026-11-08。用户提供的条件：Hi3D 生成额度充足；制作时间半天；团队会用 Godot 和 Three.js。以下是待选的实施建议，尚未开始实现，也不代表已经完成工期验证。

## 选型结论

**首选：Godot，本地双人纯合作《遗迹搬运》（玩法暂名）。** 两名机器人共同将一件宝物送到出口，沿途互相配合开启机关。固定斜俯视镜头、一个场景、三段挑战、一次 3–5 分钟完整通关。

**独立备选：Godot，本地双人纯对战《悬浮炮台决斗》（玩法暂名）。** 同一张小型竞技场，两人移动、发射慢速能量弹，先取得指定击倒数者获胜。只做对战，不实现合作关卡。

两条路线只选一条。相比此前的射击或动作冒险建议，这次优先降低骨骼动画、瞄准镜头和复杂物理约束的接入成本。团队两套技术都能用的前提下，建议先用 Godot 的场景、输入和物理工作流；如果团队已有可运行的 Three.js 模板，沿用模板可能更快，应优先比较第一段可玩循环的搭建速度。

## Hi3D 用在哪里

[Hi3D 官方文档](https://docs.hi3d.ai/en/)列出了图生 3D、纹理、拆件及 GLB、FBX、OBJ 等导出能力。[官方 Agent 页面](https://www.hi3d.ai/zh/hi3d-agent)也介绍了人形绑定与动画能力；半天原型仍建议采用机器人、悬浮装置和静态道具，让骨骼流程不成为交付依赖。

[官方 FAQ](https://docs.hi3d.ai/en/api/getting-started/faq)说明生成精度会影响文件与推理时间，并列出较高面数的生成目标。因此额度充足不等于可以无限接入模型：仍需筛选、导入、统一比例、简化碰撞并验证帧率。此处尚未实际生成或导入资产，具体耗时与性能待测试。

- Hi3D 生成可辨识的宝物、机器人外观、门、柱子和装饰；首版选 6–8 种最终模型即可。
- 先导入一个 GLB 验证材质、朝向、尺寸和性能，再批量生成。格式支持不保证任意生成结果都无需调整。
- 玩法物体使用简单盒体、球体或胶囊碰撞；视觉网格挂在玩法节点下，不直接依赖精细网格的形状。
- 地板、坡道、桥和门洞先用引擎几何体搭建，保证可走、可推、可通行，再加装饰。
- 允许并行生成多个外观供筛选，但不增加首版关卡、技能或物理交互种类。
- 生成流程作为开发工具，不要求玩家在游戏中等待模型生成。

## 首选合作方案：遗迹搬运

### 核心体验

两人共同把球形宝物推到出口，目标和胜负完全共享。双方分别有不同颜色的机关权限：一人开路时另一人护送宝物，然后交换职责。两人都能正常移动和推宝物。

三段挑战依次为：

1. 开阔通道：共同推宝物到感应台，学习操作与目标。
2. 双机关：两人分别进入各自权限区，开启宝物通路；开门后继续共同运送。
3. 简单坡道：一人保持机关开启，另一人推宝物到安全区，再共同抵达出口。

这是关卡草案，需要试玩检查是否有人长期等待、是否可以由一人包办。首版不用绳索、布娃娃、人物攀爬或精密抓取。若宝物物理不稳定，改为按固定速度滑动的可推物体，仍保留合作机关。

### 3D 展示点与资产清单

俯视镜头能看到宝物、角色、机关和遗迹层次；坡道、立柱与高低差参与空间体验。避免长时间遮住角色的建筑。

| 资产 | 数量控制 | 接入方式 |
| --- | --- | --- |
| 机器人外观 | 1 个基础模型，两种颜色 | 简单碰撞体 + 平移、转向和轻微浮动；不依赖骨骼 |
| 宝物 | 1 个最终外观 | 球形碰撞体，生成网格仅作视觉表现 |
| 柱子、石像、箱子 | 3 种以内 | 静态装饰，必要时配盒体碰撞 |
| 门、终点装置 | 各 1 种 | 引擎控制移动或发光；无法稳定拆件则整体平移 |
| 地板、坡道、机关按钮 | 引擎几何体 | 尺寸与可玩性优先 |

建议生成时保持同一材质语言与配色，主体单独、轮廓清楚、结构简单；涉及连接和通行尺寸的模块由代码或引擎控制，不依赖生成结果精确吻合。

## 若选纯对战：悬浮炮台决斗

保留一张竞技场、同一机器人外观、移动、慢速弹道、血量和复位，60–90 秒一局。双方固定朝向对方或采用简化自动瞄准，先去掉复杂鼠标瞄准与第三人称镜头。装饰可由 Hi3D 生成，掩体碰撞使用简单形状。

只围绕击败对手设计，不加入合作任务、敌人 AI、多武器、升级、联网匹配或角色差异。验证能否看懂弹道和命中、是否存在无解角落，以及是否愿意马上再战。竞技场的装饰需要服务可读性。

## 半天安排

按 **4–6 小时**作为规划假设；实际可用时长未进一步确认。下表以 4 小时核心交付为目标，额外时间留给修复和展示，不用于扩功能。

| 时间 | 开发主线 | 资产与试玩可并行进行的工作 |
| --- | --- | --- |
| 0:00–0:20 | 锁定一条路线，测试两人输入、镜头和单模型导入 | 生成基础角色与核心道具，确定统一风格 |
| 0:20–1:10 | 用几何体做出移动、核心交互、胜负和重开 | 筛选模型，检查尺寸、材质、碰撞和面数 |
| 1:10–2:10 | 合作做三段机关；对战做完整单局，只实现所选路线 | 逐个替换视觉模型；每次确认操作未受影响 |
| 2:10–3:00 | 接入基本音效、目标提示与反馈，修复卡住和复位 | 两名真实玩家反复试玩，记录最明显的问题 |
| 3:00–4:00 | 停止加功能，导出并在另一台机器运行，录制演示 | 整理运行说明、模型来源和 Hi3D 生成过程展示 |
| 额外 0–2 小时 | 修复、优化与演示演练 | 只替换明显不合适的模型，不增加核心系统 |

如果团队至少两人，可由一人推进游戏闭环，一人负责生成与接入检查，然后一起试玩；不是要求固定团队人数。联网需求未确认，当前建议用本地双人控制制作范围；必须联网时需要重新缩减内容。

## 完成标准

- 两人可从开始界面进入游戏，输入互不冲突。
- 无需开发者口头解释即可知道目标；能完整通关或分出胜负。
- 失败后可以重开，宝物或玩家卡住时可复位。
- 最终模型已导入，材质可见，目标机器帧率可接受。
- 导出版本在另一台机器实际运行；README 给出控制方式与运行方法。
- 文档与代码检查通过后及时 commit / push；模型引入公开仓库前记录来源与适用使用条款，不把生成资产默认当作 MIT 代码。

半天内最有价值的成果是一个两人愿意玩完的闭环，加上几件有辨识度的生成资产。生成数量作为筛选空间，最终接入数量受可玩性与性能约束。
